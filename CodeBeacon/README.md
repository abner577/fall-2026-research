# CodeBeacon: research execution and application

`CodeBeacon/` is the working root for carrying out the research. The repository has two main folders: this folder for execution and [fall-2026-research/](../fall-2026-research/) for the planning and meeting record. The repository-level [README](../README.md) and [research plan](../research-plan.md) provide overall context.

Put the evaluation study's actual materials here: the coherent IoT test project and its controlled versions, vulnerability placement explanations, independently reviewed answer keys, exact prompts and revisions, scanner configurations and commands, run settings, complete raw responses and reports, errors, screenshots, images, verification evidence, grading, scores, comparisons, and conclusions from the experiments. Keep answer keys and injection notes separate from the project inputs given to detectors.

Use this folder for the working designs and architecture that guide execution, including revisions to the earlier proposals. If application development proceeds, its code, configuration, tests, documentation, and related assets also belong here. The evaluation project is study material; it is distinct from the optional CodeBeacon application being developed later.

The earlier planning notes, proposal diagrams, architecture discussions, and supporting images remain under [fall-2026-research/](../fall-2026-research/). Consult [the planning notes](../fall-2026-research/coming-up-w-research-plan/evaluation-plan.md) and [meeting records](../fall-2026-research/docs/) for their rationale and status. Weekly transcripts, preparation, checklists, and meeting conclusions continue to belong in `fall-2026-research/docs/`, including future meetings. Experimental conclusions and run evidence belong here.

AI assistants should read the planning and meeting context before acting, then save execution work under `CodeBeacon/`. Preserve exact inputs, code versions, prompts and revisions, complete outputs, errors, commands, configurations, settings, versions, dates, and reasons for changes. Keep raw evidence separate from normalized results and retain practice and unsuccessful runs. Record why and where each vulnerability was inserted and how and by whom it was verified. Do not present a proposed design, illustrative output, or unchecked answer key as a completed experiment or validated result.

The three selected scanners are Semgrep Community Edition, CodeQL, and Snyk Code, using Snyk's free plan only. The comparison remains the first milestone; application development depends on the findings and available time. This README establishes where work belongs; detailed subfolders can be chosen as the study is implemented, and no experiment, codebase, or completed implementation is implied by this guide.
