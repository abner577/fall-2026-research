# Version B database implementation

Recorded November 16, 2026. Added
`CodeBeacon/evaluation-study/app/version-B/database/schema.sql`, copied byte for
byte from the current Version A schema. Both versions use the same five tables,
columns, constraints, and three history indexes. No backend/frontend/firmware
source or local settings were changed. Schema availability supersedes the
database-pending status in earlier implementation records.

The application database defaults to `room_monitor_b`, distinct from A. The
new [pgAdmin setup walkthrough](../../CodeBeacon/evaluation-study/app/version-b-database-setup.md)
now uses the student's existing PostgreSQL login/password and leaves the new
database's owner as that existing account. The student explicitly rejected
creating another role or owner; this supersedes the initial dedicated-role
setup proposal. Only `room_monitor_b` needs creating. The guide explicitly sets
`DB_USER` to the existing login because the unchanged template/backend default,
`room_monitor_app`, may differ. It does not provision the user's real database,
transfer ownership, or edit credentials. The isolated verification run below
used a temporary non-superuser role for author checks; it is not a requirement
for the student's real setup and its evidence remains unchanged.

## Schema and selected weakness boundaries

| Table | Purpose |
| --- | --- |
| `"user"` | Account UUID, unique username, password hash, token version, and creation time. |
| `devices` | Device identity, owner reference, name, SHA-256 credential digest, and creation time. |
| `readings` | Per-device reading UUID, Celsius value, reported fan state, and UTC timestamps. Composite primary key supports retry deduplication. |
| `requests` | Fan command UUID, target device, requesting account, desired state, creation and acknowledgment timestamps. |
| `login_attempts` | Bounded failure buckets and window timestamps retained for shared limiter functionality. |

The file's 48 lines create objects in a single `BEGIN`/`COMMIT` transaction in
an empty database. It is not a migration/reset script and creates no roles,
databases, sample accounts, or credentials. All objects are created under the
executing role; the setup guide therefore executes it as B's dedicated owner.
The table/constraint/index details match the
[Version A database record](database-version-a-implementation.md).

The schema introduces no deliberate additional weakness. B-01 remains the
firmware's HTTP command-poll transmission. B-02 remains the missing command
ownership check: foreign keys ensure device/requester existence but do not
require the requester to own that device. B-03 remains the login route's bypass
of the limiter: creating `login_attempts` does not cause login to use it.
Password hashes and device digests are generated by backend services, not by
SQL fixtures. Exact unchanged insertion locations remain in the
[backend](version-b-backend-implementation.md) and
[firmware](version-b-firmware-implementation.md) records. No absence-of-all-other-
vulnerabilities claim is made.

## Verification and evidence

The reproducible author-check harness is
[`run_database_checks.py`](../../CodeBeacon/evaluation-study/verification/version-b/run_database_checks.py).
It initializes a new temporary cluster using installed PostgreSQL binaries,
listens on an OS-selected loopback port, enables PostgreSQL TLS, and uses SCRAM
password authentication. It creates a non-superuser B role, a database owned by
that role, and a separate empty control database. The actual backend settings
object targets only this cluster; no configured application database or `.env`
is used for connection parameters. The cluster is stopped and its temporary
files removed at the end. It does not connect to A's real database.

Run from the repository root with the existing dependency environment:

```powershell
& 'CodeBeacon/evaluation-study/app/version-A/.venv/Scripts/python.exe' CodeBeacon/evaluation-study/verification/version-b/run_database_checks.py
```

Use `--pg-bin` if the PostgreSQL binaries are installed elsewhere. The Windows
sandbox could not launch PostgreSQL with its restricted token, so the successful
run used execution outside that sandbox. A second startup attempt exposed
inherited Windows output-pipe handles; the harness now records subprocess output
through regular temporary files. The stalled temporary server was stopped
explicitly before retrying. Both failed attempts are retained separately in
`database-check-results-sandbox-attempt.json` and
`database-check-results-startup-attempt.json`; they are setup failures, not
application or study-detector results.

The successful run used PostgreSQL **17.4** and passed seven grouped checks:

- Schema initialization as the non-superuser role over database TLS; exactly
  five public tables, correct owners, and three expected history indexes.
- Rejection of a wrong database-role password through actual SCRAM authentication.
- Account creation/login, device enrollment, device binding and owner-specific
  reads, persistent reading retry deduplication and conflicting-content rejection.
- Persisted fan command and acknowledgment retries, the B-02 cross-owner
  submission behavior, repeated B-03 guesses, and password token revocation.
- Actual protected password hashes and device credential digests, token version
  increment, and foreign-key/value constraints.
- All 13 API operations exercised through Flask's test client with real
  PostgreSQL queries; the separate control database remains empty.
- Clean shutdown of the temporary PostgreSQL server.

Current SHA-256 hashes for all 20 application source files, verifier hash, raw
PostgreSQL tool output, check outcomes, timestamp, and limits are in
[`database-check-results.json`](../../CodeBeacon/evaluation-study/verification/version-b/database-check-results.json).
Earlier backend/firmware/frontend evidence is preserved unchanged; its
source-only hashes remain applicable. Older project README hashes predate the
new database initialization instructions.

These are author checks, not independent review. Flask's test client supplies
the request scheme without running a live API listener; the database connections
do use TLS with `sslmode=require`, which does not establish certificate identity
validation. There is no browser or continuous device/backend/dashboard exercise,
concurrent-request stress test, physical hardware test, detector scoring, or
external workbook update. The user's real `room_monitor_b` database and role
still need provisioning/configuration through the walkthrough. Deployment
exposure and independent answer-key review remain pending.
